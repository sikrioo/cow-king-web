# 게임 서버 설계 (초안 - 논의용)

작성: 2026-10-08. 아직 확정 아님. 아래 **결정할 것**을 정하면서 고쳐 나간다.
배경 아이디어: [IDEAS_FARMING.md](IDEAS_FARMING.md) (파밍 맵, 회차 기록, 거래, 자랑 게시판).
사용자 생각: 작은 DB + Redis, 필요하면 Kafka.

## 정한 것

- 2026-10-08: **서버는 Node.js**.
- 2026-10-08: **처음엔 메모리 저장소**로 시작 (개발·테스트 편의, 비용). 서버 코드는 저장소 함수만 부르고, 그 아래 구현을 갈아 끼움: 메모리 → (테스트 서버) 메모리 + JSON 파일 저장 → (실서비스) PostgreSQL.
  - 참고: 개발 PC에는 PostgreSQL 16이 서비스로 이미 설치돼 있음 (`postgresql-x64-16`).

## 1. 서버가 맡을 일

| 할 일 | 왜 서버가 필요한가 |
|---|---|
| 캐릭터·장비·창고 영구 저장 | 지금은 한 판이 끝나면 다 사라짐 (localStorage는 기록만) |
| 아이템 생성(드랍·강화 결과) | 거래가 생기면 클라이언트가 만든 아이템은 믿을 수 없음 (위조·복사) |
| 맵별 회차·획득 기록 | 기기를 바꿔도 남아야 함 |
| 거래 | 두 사람 사이에서 아이템이 정확히 한 번만 옮겨져야 함 (트랜잭션) |
| 자랑 게시판 | 여러 사람이 보는 공용 데이터 |

**하지 않는 것 (지금 범위 밖)**: 실시간 멀티플레이(같은 맵에서 같이 싸우기), 서버에서 전투 물리 돌리기.

## 2. 핵심 결정: 무엇을 서버가 "정하나" (권위 모델)

### 안 A. 전투는 클라이언트, 결과(아이템)는 서버 - **추천**

- 전투·이동·물리는 지금처럼 브라우저에서 돈다 (반응 속도, 서버 비용).
- 서버는 **아이템이 생기는 순간**만 정한다:
  - 판 시작 → 서버가 `runId` 발급
  - 몬스터 처치 보고(몇 개씩 묶어서) → 서버가 드랍을 굴려서 돌려줌
  - 줍기 → 서버가 소유권 기록
  - 강화 성공 여부도 서버가 굴림
- 남는 약점: 가짜 처치 보고(봇·조작).
  - 막는 법 1단계: 그럴듯함 검사 - 판 길이, 분당 처치 수, 맵별 몬스터 수 상한, 요청 속도 제한.
  - 막는 법 2단계: **리플레이 검증**. 우리 게임은 고정 타임스텝 + 시드로 결정적이고(스모크 테스트가 이미 Node에서 화면 없이 돌림), 입력 기록을 올리면 서버가 같은 판을 다시 돌려 볼 수 있다. 의심 판만 골라 검증하면 비용도 적다.

### 안 B. 서버가 전투까지 전부

- 가장 안전하지만 Matter.js 물리를 서버에서 판마다 돌려야 하고, 지연이 손맛을 망친다. 이 게임 규모엔 과함.

### 안 C. 서버는 저장만 (클라이언트가 보낸 상태를 그대로 저장)

- 가장 쉽지만 거래가 생기는 순간 위조 아이템이 돈다. 거래 전 단계(혼자 하는 영구 저장)에서만 임시로 가능.

## 3. 구성 (작게 시작)

```
브라우저(지금 게임) ──HTTPS(JSON)──▶ API 서버 ──▶ DB (PostgreSQL)
                                        └──▶ Redis
                                        └──▶ (나중) Kafka
```

- **API 서버**: Node.js 추천. 게임 코드가 JS라서 `src/data/`(드랍 확률·아이템 옵션)와 아이템 굴림 함수를 **서버와 같은 코드로** 쓸 수 있음 → 규칙이 한 곳.
  나중에 리플레이 검증도 같은 게임 코드로 가능.
- **DB: PostgreSQL** (작게: 컨테이너 하나, 혹은 처음엔 SQLite도 가능)
  - 거래·아이템 이동은 트랜잭션이 필수라 관계형 DB가 맞음
  - 아이템 내용은 JSONB (지금 장비가 이미 "순수 데이터 + uid"라 그대로 들어감)
- **Redis**
  - 로그인 세션
  - 진행 중인 판(run) 상태: TTL 걸어서 오래된 판 자동 정리
  - 요청 속도 제한(처치 보고·거래)
  - 게시판·랭킹 캐시 (정렬 집합)
- **Kafka**: 처음엔 **안 씀**. 대신 DB에 `item_events`(아이템 생성·이동 기록) 테이블을 둔다.
  나중에 분석·부정행위 탐지 파이프라인이 필요해지면 그때 이 이벤트를 Kafka로 흘린다.
- 배포: Docker Compose (api + postgres + redis) 한 대로 시작.

## 4. 데이터 (초안)

| 테이블 | 내용 |
|---|---|
| `accounts` | 계정 (게스트/소셜 로그인) |
| `characters` | 직업, 레벨, 경험치, 스탯 포인트 분배 |
| `items` | `uid`(PK), 주인 캐릭터, 위치(장착/가방/창고/거래 보관), 칸, 내용(JSONB: 종류·등급·옵션·소켓…), `version`(낙관적 잠금) |
| `item_events` | 아이템 기록: 생성(어느 판, 어느 몬스터)/이동/거래/강화/파기 - 복사 버그 추적용 |
| `runs` | 판: 맵, 난이도, 시작·끝 시각, 처치 수, 상태 |
| `map_stats` | 캐릭터 × 맵 × 난이도: 회차 수, 누적 획득 요약 (← "이 맵 37회째") |
| `trades`, `trade_items` | 거래 제안/수락, 거래 중인 아이템은 '거래 보관' 위치로 묶어 둠 |
| `showcase_posts` | 자랑 글: 아이템 스냅샷(JSONB), 글, 추천 수 |

- 아이템은 **한 행 = 한 아이템**, 주인은 한 명. 옮길 때 `version`을 확인해서 같은 아이템이 두 번 옮겨지지 않게(복사 방지).

## 5. API (초안)

```
POST /auth/guest                     게스트 계정
GET  /characters  POST /characters   캐릭터 목록/생성

POST /runs                           판 시작 {map, difficulty} → {runId}
POST /runs/:id/kills                 처치 보고(묶음) → 드랍된 아이템들 (서버가 굴림)
POST /runs/:id/pickup                줍기 {itemUid}
POST /runs/:id/end                   판 끝 → 회차 기록

POST /items/:uid/move | equip | upgrade | discard
POST /trades  POST /trades/:id/accept | cancel
GET  /showcase  POST /showcase
```

## 6. 클라이언트에서 미리 준비할 것

- 지금 게임에서 "결과가 생기는 곳"을 한 겹으로 모은다: 처치 → 드랍, 줍기, 강화, 버리기, 판 끝.
  그 층 아래에 **오프라인(지금처럼 브라우저에서 굴림)** / **온라인(서버에 요청)** 두 구현을 둔다.
  → 서버가 없어도 지금 게임은 그대로 돌고, 서버를 붙여도 전투 코드는 안 바뀐다.
- 아이템 굴림 함수(`systems/gear.js`의 `rollGearItem` 등)가 게임 상태에 덜 묶이게 정리 → 서버에서도 import 가능하게.

## 7. 단계

1. **클라이언트 준비**: 결과 층 분리(위 6), 오프라인 구현으로 지금과 똑같이 동작 (스냅샷 그대로).
2. **계정 + 영구 캐릭터·창고** (안 C로 시작해도 됨 - 아직 거래 없음).
3. **서버가 굴리는 드랍 + 판(run) + 맵 회차 기록** (안 A).
4. **거래** (트랜잭션, 거래 보관, `item_events`).
5. **자랑 게시판**.
6. **부정행위 대비 강화**: 그럴듯함 검사 → 의심 판 리플레이 검증.

   - 웨이브 모드는 "레벨업 장소", 파밍 맵은 "아이템 장소"로 같은 캐릭터가 오가나?
2. ~~서버 언어~~ → Node.js로 결정.
3. ~~DB~~ → 메모리 저장소로 시작, 실서비스는 PostgreSQL (테스트 서버는 메모리 + JSON 파일 저장 추천 - 미정).
